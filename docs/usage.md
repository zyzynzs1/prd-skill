# 使用指南

本文说明 prd-writer 技能的五种使用模式、产物约定、分段生成、测试用例、校验脚本自查与常见追问。安装方法见 [安装指南](install.md)；技能本身的规则以 `prd-writer/SKILL.md` 为准。

使用前注意：技能读取的是**当前会话工作区**的代码。请先在目标代码仓库中打开会话，再发起需求；对空仓库或不包含实现的仓库，技能会拒绝编造功能。

## 1. 五种模式与对话示例

技能先判断要做哪一种事，再按对应流程执行。用户未说明时默认按模式 A 处理。

### 1.1 模式 A：完整生成

适用：给已有代码仓库补写、补全 PRD。

```text
用户：给这个仓库补一份 PRD，覆盖整个后台管理系统，版本 V1.0，主要读者是研发和 UI。

技能：（阶段 0）读取 README 与 package.json，识别出 Vite + Vue 3 项目，包含用户、订单、
      统计三个模块。确认三个问题：PRD 覆盖范围是三个模块全量还是只写 V1 已上线部分？
      目标读者是否包含 QA？迭代如何划分？

用户：三个模块全量，读者包括 QA，迭代按模块分两期。

技能：（产出范围摘要）随后扫描路由、页面、接口、数据模型，输出功能盘点表，
      每条功能带代码证据与置信度；请用户增删改。

用户：订单模块的「批量导出」先不写，其他可以。

技能：（阶段 2）提问 ≤5 个代码中拿不到的信息，例如导出上限、权限角色、上线时间；
      （阶段 3）提交功能清单、迭代规划、功能框架图草图等待确认；
      （阶段 4）按迭代起草；（阶段 5）逐项过质量门禁并运行校验脚本；
      （阶段 6）按交付指南转 Word、渲染框架图，并按需嵌入测试用例 Excel 后打开。
```

产物包括功能盘点、PRD 的 Markdown 与 Word 文件，以及遗留的【待确认】项说明。

### 1.2 模式 B：增量更新

适用：已有 PRD 需要局部修改。

```text
用户：把 PRD 里 1.2「草稿自动保存」的限制条件改一下：自动保存间隔从 30 秒调整为 10 秒，
      其他内容不动。

技能：只读取 1.2 小节与对应代码，输出变更后的完整 1.2 小节（便于整体替换），
      同步更新该功能点的「更新时间」，并在「文档说明」的修订记录表追加一行。
      本次不涉及功能点增删，因此 PRD 的「功能清单」与「功能框架图」两节不变。
      若 1.2 已有测试用例，提示需要同步更新的用例范围。
```

增量更新不会重写未涉及的章节，也不会批量刷新全文的「更新时间」。

### 1.3 模式 C：评审

适用：检查已有 PRD 是否完整、可执行、可测试。输出评审报告，不直接修改文档。

```text
用户：评审 docs/prd/PRD-在线考试系统-V1.0.md，重点看可测性和功能一致性。

技能：按完整性、一致性、可执行性、可测性、证据支撑、语言规范六个维度逐项检查，
      输出问题表（序号 / 文档位置 / 问题类型 / 严重级别 / 问题描述 / 证据或依据 / 修改建议）
      与结论（通过 / 有条件通过 / 不通过），并给出问题统计。
      例如：第三部分「1.2 交卷」的限制条件缺少失败重试规则，可测性不足，级别：重要。

用户：按报告修复阻塞项和重要问题。

技能：转为模式 B，逐条给出变更后的小节与修订记录。
```

### 1.4 模式 D：仅功能盘点

适用：先对齐功能范围，暂不写正文。

```text
用户：先只梳理这个仓库的功能点，不要写 PRD 正文。

技能：执行范围确认与功能盘点，输出功能盘点表（功能模块 / 大功能点 / 子功能 / 代码证据 /
      置信度 / 建议迭代），结尾给出建议迭代划分与待确认清单，不转 Word。
```

确认盘点结果后，可以接着说「按这份盘点生成完整 PRD」，即模式 D → A。

### 1.5 模式 E：测试用例

适用：PRD 正文已确认，需要生成或补充测试用例。

```text
用户：生成迭代 1 的测试用例。

技能：读取 prd-writer/references/testcase-spec.md 与迭代 1 的正文，按 8 列固定表头
      （序号 / 关联功能点 / 用例名称 / 场景类型 / 前置条件 / 测试步骤 / 预期结果 / 优先级）
      覆盖正常流程、异常操作、边界条件、权限校验四类场景；
      「具体说明」每个叶子条目与「限制条件」每条规则至少被 1 条用例覆盖。
      超过 30 条时按场景类型拆分为 4 张子表。
      交付时以嵌入 Excel 对象插入 Word 对应位置，不使用 Word 原生表格或截图代替。
```

未指定迭代时默认最近一个迭代。

## 2. 产物命名与目录约定

默认产物如下；用户指定路径时以用户指定为准。

| 产物 | 命名 | 建议位置 |
|------|------|----------|
| 功能盘点 | `功能盘点-{产品/模块}.md` | `docs/prd/` |
| PRD 草稿 | `PRD-{产品/模块}-V{x.y}.md` | `docs/prd/` |
| PRD 交付 | `PRD-{产品/模块}-V{x.y}.docx` | `docs/prd/` |
| 测试用例附件 | 由交付环节内嵌，不单独命名 | 嵌入 PRD Word 内 |

本仓库的 `.gitignore` 默认忽略 `docs/prd/` 与 `output/`，避免把生成的文档误提交；如需纳入版本管理，可按团队规范调整。

交付格式说明：

- 最终交付物是 Word（`.docx`）。Markdown 草稿先经用户确认，再转 Word。
- Word 中各级标题与「具体说明」条目使用自动多级编号，不使用手打数字文本。
- 功能框架图渲染为 PNG 插入，Word 中不保留 markmap 代码块。
- 测试用例以嵌入的 Excel 对象呈现，便于 QA 双击编辑、筛选与导出。
- 交付环节按 `prd-writer/references/delivery-guide.md` 的流程执行，并说明产物路径与遗留的【待确认】项。

注意：本仓库**不包含**一键把 Markdown 导出为 docx 的脚本。Word 交付依赖 `prd-writer/references/delivery-guide.md` 中记录的工具链（例如 pandoc、python-docx、docxtpl、Word / WPS COM），需要本机具备对应工具；工具缺失时技能会给出可执行的替代步骤，不会静默降级。

## 3. 分段生成与继续

功能点较多时，单次输出可能超出模型上限。技能会在生成前估算长度，主动按迭代或大功能点分段，每段结构完整，段尾标注：

```text
（第 1/3 段完，回复「继续」生成下一段）
```

继续方式：

1. 同一会话内直接回复「继续」，技能从断点处生成下一段。
2. 换到新会话时，说明已有文件与断点，例如：

   > 上次生成到一半，文件在 docs/prd/PRD-在线考试系统-V1.0.md。请读取现有内容，从迭代 2 继续，不要重写已完成部分。

技能会读取现有 PRD，判断缺失章节，从断点所在迭代继续。

分段禁止在句子、表格或字段中间截断；如发现截断，指出位置后要求补齐。

## 4. 如何触发测试用例

- demo 未定型阶段默认**不生成**测试用例，各迭代附件位写「【测试用例待生成：demo 定型后统一生成】」。
- 需要生成时，在对话中明确指令，例如「生成测试用例」「生成迭代 2 的测试用例」「只补权限校验类用例」。
- 技能先读取 `prd-writer/references/testcase-spec.md` 与对应迭代正文；正文不完整时，会先提示补全再生成，避免用例缺少依据。
- 用例必须可追溯到功能点编号与「具体说明」叶子条目；无法对应的内容会标【待确认】，不编造测试步骤。

## 5. 用校验脚本自查

`prd-writer/scripts/validate_prd.py` 是随技能提供的结构与一致性校验器，覆盖质量门禁中可机械判断的部分（结构、字段、编号、功能数量一致性、占位符、字面量 HTML 实体等）。它**不做内容质量判断**，业务正确性、交互深度、证据是否充分仍需按 `prd-writer/references/quality-checklist.md` 人工核对。

### 5.1 基本用法

在本仓库根目录执行。已安装到目标项目时，把脚本路径换成实际技能目录，例如 `.trae/skills/prd-writer/scripts/validate_prd.py`。

```bash
# 校验一个或多个 PRD Markdown 文件
python prd-writer/scripts/validate_prd.py prd-writer/examples/PRD-示例-在线考试系统.md

# 校验技能文件本身（frontmatter、行数、引用路径）
python prd-writer/scripts/validate_prd.py --skill prd-writer/SKILL.md

# WARN 也视为失败，适合交付前严格自检
python prd-writer/scripts/validate_prd.py --strict docs/prd/PRD-在线考试系统-V1.0.md

# 以 JSON 输出，便于接入其他工具
python prd-writer/scripts/validate_prd.py --json docs/prd/PRD-在线考试系统-V1.0.md

# 隐藏 INFO 信息
python prd-writer/scripts/validate_prd.py --quiet docs/prd/PRD-在线考试系统-V1.0.md
```

### 5.2 结果含义

| 退出码 | 含义 |
|--------|------|
| 0 | 未发现 ERROR（`--strict` 时还需无 WARN） |
| 1 | 存在失败项 |
| 2 | 用法错误或文件不存在 |

报告中的级别：

- `ERROR`：结构或字段不合规，必须修复；
- `WARN`：建议修复，`--strict` 下视为失败；
- `INFO`：统计信息，如功能数量、待确认条数。

报告会给出文件行号，便于定位。修复后重跑，修复循环建议不超过 3 轮；仍有未通过项时，应在交付说明中如实列出。

### 5.3 在流程中的位置

校验脚本属于阶段 5「自查与门禁」的可选工具。技能可运行时先跑脚本，再按质量门禁逐项人工核对；脚本不可用时，按 `prd-writer/references/quality-checklist.md` 手工检查。

Windows 终端如果中文输出乱码，先执行 `chcp 65001` 再运行脚本。

## 6. 常见追问

**Q1：为什么必须先做功能盘点，不能直接写 PRD？**

功能盘点把代码中的事实转成可核对的清单，是 PRD 的证据来源，也是与用户对齐范围的抓手。跳过盘点直接写正文容易编造功能。用户明确要求「先按代码快速出草稿」时，技能会在草稿中标注假设，并说明未完成盘点。

**Q2：代码里找不到依据的信息怎么处理？**

一律标注【待确认】，禁止编造数据、时间、人名、指标；所有【待确认】项汇总到 PRD 文末的「附录 A、待确认清单」，写明位置、问题、影响与建议确认人。

**Q3：功能盘点里的代码证据会出现在 PRD 正文里吗？**

不会。PRD 正文以产品语言呈现，不暴露代码路径；代码证据保留在功能盘点和评审材料中，便于评审核对。

**Q4：生成内容太长被截断怎么办？**

技能会主动分段，不会在句子、表格或字段中间截断。若输出仍被截断，回复「继续」即可；换会话时提供已有文件路径与断点位置，技能会从断点续写，不重写已完成部分。

**Q5：能直接生成 Word 吗？**

交付目标是 Word，但流程是先产出 Markdown 草稿、经用户确认后再转换，避免格式返工。仓库没有自动导出脚本，转换按 `prd-writer/references/delivery-guide.md` 的工具链执行；本机缺少工具时，按指南给出的替代步骤操作，并在交付说明中注明。

**Q6：为什么不默认生成测试用例？**

demo 未定型时功能细节仍可能变化，提前生成会大量返工。PRD 各迭代先保留附件位，用户明确要求后再生成，并保证用例与功能点、限制条件可追溯。

**Q7：能评审别人写的 PRD 吗？**

可以。使用评审模式，技能只输出问题表与结论，不直接改文档；需要修复时再转增量更新模式逐条修改。

**Q8：技能会修改业务代码吗？**

不会。技能只读取代码作为证据，产出是文档；除用户明确要求写入的文档文件外，不修改仓库代码。

**Q9：支持哪些技术栈？**

技能按路由、菜单、页面组件、接口定义、数据模型、权限配置、定时任务等线索做技术栈无关的盘点，不依赖特定框架；无法识别的仓库会说明原因并给出手工盘点建议。

**Q10：如何确认技能版本与文档一致？**

查看 `prd-writer/SKILL.md` 的 frontmatter 版本、仓库 `CHANGELOG.md` 与 `README.md` 的版本说明，三者应为同一版本号（当前为 `2.0.0`）。
