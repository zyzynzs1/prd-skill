# 访谈指南

> **何时读取本文件**：SKILL.md 阶段 2「访谈补全」开始时读取；前置条件是阶段 1 功能盘点已完成（见 `references/code-analysis-guide.md`）。当需要向用户补齐代码无法推断的信息，或用户要求先明确需求范围时，同样读取本文件。本文件提供提问原则、四批访谈节奏、P0/P1/P2 分层问题库、提问话术、默认策略、必须问与可推断的判定标准、访谈记录模板。 本文件中的引用路径均相对技能根目录（SKILL.md 所在目录）。

## 目录

1 定位与边界；2 七条提问原则；3 四批问题；4 分层问题库（4.1–4.7）；5 提问话术模板；6 默认策略表；7 必须问 vs 可推断；8 访谈结果记录模板；9 结束访谈的判定；10 答案落入 PRD 的章节；11 常见错误与纠正。

## 1. 访谈的定位与边界

- 访谈只解决「代码里没有答案」的问题：业务背景、产品目标、范围与版本、读者、迭代与排期、验收标准、设计偏好。
- 访谈不替代功能盘点：页面、路由、字段、校验、权限点、接口返回等以代码证据为准；代码能确认的不得占用提问额度。
- 访谈的输入是 `功能盘点.md`：盘点中的低置信度项与【待确认】项按 P0/P1 优先级转为问题；已确认的代码事实不重复提问。
- 访谈不改写用户决策：用户给出的事实与偏好原样记录；与代码证据冲突时并列记录并请用户裁决，禁止自行取舍。
- 访谈产出必须可追溯：每个答案标注来源（用户口述 / 代码证据 / 默认值）与状态（已确认 / 【待确认】）。
- 访谈不是一次性事件：增量更新与评审阶段产生的新缺口，按同样原则单点补问，不重跑全部批次。

## 2. 七条提问原则

1. **一次不超过 5 个问题**：单轮提问按 P0、P1、P2 排序取前 5 个，答完再发下一批。
2. **能推断的不问**：可从代码、README、依赖配置、路由表、样式文件、设计 token 推断的信息不得提问（对照第 7 节）。
3. **先封闭后开放**：优先给选项与默认值让用户选择；开放题只用于业务背景、产品目标、验收标准。
4. **每个问题说明用途**：一句话说明答案将写入哪一节，降低用户回答成本。
5. **拒答或不确定不阻塞**：给出默认值并标注【待确认】，继续后续批次。
6. **不预设答案**：不在问题中加入倾向性描述，不给用户反向暗示。
7. **关键项复述确认**：范围与版本、目标读者、迭代划分、上线时间四类信息，起草前一次性复述确认。

## 3. 提问节奏：四批问题

| 批次 | 发送时机 | 目标 | 覆盖主题 | 结束条件 |
|---|---|---|---|---|
| 第 1 批 | 功能盘点完成后立即发送 | 锁定范围与文档基线 | 范围与版本、读者与用途 | 产品/模块范围、版本号、读者均有答案或已标【待确认】 |
| 第 2 批 | 第 1 批答复后 | 补齐业务与角色 | 业务背景与目标、角色与权限 | 一句话价值与产品目标可写出；角色清单可对应功能 |
| 第 3 批 | 起草前 | 锁定迭代与排期 | 迭代与排期、设计规范 | 每个大功能点有归属迭代；时间范围有值或标【待确认】 |
| 第 4 批 | 起草完成、交付前 | 锁定验收与交付偏好 | 验收标准、交付偏好 | 验收标准可测；交付格式与工具链已确认 |

- 问题在整轮访谈中连续编号（Q1、Q2……），便于用户按编号答复与追溯。
- 用户一次性答完多批时，跳过重复提问，直接进入下一未覆盖主题。
- 用户只答部分问题时，按「已答落地、未答标【待确认】」处理；同一问题最多追问 2 次。

## 4. 分层问题库（P0/P1/P2）

问题优先级（与功能优先级同名不同义，勿混用）：

- **P0**：缺失则无法开始起草，必须在本轮访谈取得答案或明确标注【待确认】。
- **P1**：影响文档准确性与可执行性，应在起草前补齐。
- **P2**：影响交付细节与阅读体验，可后补，不阻塞起草。

### 4.1 范围与版本

| 编号 | 问题 | 层级 | 适用条件 |
|---|---|---|---|
| Q1 | 本次文档覆盖的产品或模块范围是什么？包含哪些页面与子系统？ | P0 | 必问 |
| Q2 | 文档对应哪个版本号（如 V1.0）？是新建版本还是更新既有版本？ | P0 | 必问 |
| Q3 | 本期明确不做的范围有哪些？ | P1 | 范围有争议或跨模块时 |

### 4.2 读者与用途

| 编号 | 问题 | 层级 | 适用条件 |
|---|---|---|---|
| Q4 | 本文档主要读者是谁（研发、UI、QA、管理层、客户）？ | P0 | 必问 |
| Q5 | 文档用途是什么（研发排期、UI 出图、QA 写用例、验收、对外交付）？ | P0 | 必问 |
| Q6 | 是否需要对外或跨团队交付？是否涉及敏感信息脱敏？ | P2 | 对外交付时 |

### 4.3 业务背景与目标

| 编号 | 问题 | 层级 | 适用条件 |
|---|---|---|---|
| Q7 | 做这个产品/功能要解决的业务痛点是什么？当前流程如何运作？ | P0 | 必问 |
| Q8 | 产品目标是什么？有无可量化指标（渗透率、转化率、效率提升）？ | P0 | 必问 |
| Q9 | 本版本要达成的目标与边界是什么？ | P1 | 多版本并行时必问 |

### 4.4 角色与权限

| 编号 | 问题 | 层级 | 适用条件 |
|---|---|---|---|
| Q10 | 系统涉及哪些角色？各自的权限边界与使用场景是什么？ | P0 | 必问 |
| Q11 | 代码中未体现的角色或权限差异是否存在？ | P1 | 功能盘点发现角色枚举或鉴权逻辑时 |
| Q12 | 是否存在跨角色访问、数据隔离或审批要求？ | P1 | 涉及多角色数据时 |

### 4.5 迭代与排期

| 编号 | 问题 | 层级 | 适用条件 |
|---|---|---|---|
| Q13 | 本期拆分为几个迭代？各迭代分别包含哪些大功能点？ | P0 | 必问 |
| Q14 | 各迭代的时间范围与发布目标是什么？ | P1 | 时间未定时标【待确认】，禁止编造日期 |
| Q15 | 大功能点的优先级如何判定？是否有强制 P0 项？ | P1 | 存在合规或主流程强依赖时 |
| Q16 | 是否存在依赖外部团队或需要前置交付的模块？ | P2 | 跨团队协作时 |

### 4.6 设计规范与交付偏好

| 编号 | 问题 | 层级 | 适用条件 |
|---|---|---|---|
| Q17 | 项目是否已有设计规范、组件库或视觉稿？以哪份为准？ | P1 | 存在设计文件时 |
| Q18 | 是否有品牌色、字体、间距等既定规则？ | P2 | 无设计规范时用默认机制 |
| Q19 | 交付格式是否为 Word？是否需要同步交付 Excel 用例与框架图 PNG？ | P1 | 交付前确认 |
| Q20 | 是否需要嵌入测试用例的 Excel 对象、是否需要生成后自动打开？ | P2 | 环境具备 Office/WPS 时 |

### 4.7 验收标准

| 编号 | 问题 | 层级 | 适用条件 |
|---|---|---|---|
| Q21 | 本期验收由谁执行？依据什么标准判定通过？ | P1 | 必问 |
| Q22 | 是否存在必须满足的合规、性能或兼容性指标？ | P1 | 涉及对外发布时 |
| Q23 | demo 定型时间与测试用例生成时机如何安排？ | P2 | 按需生成用例时 |

## 5. 提问话术模板

**模板 1：批次开场（附盘点结论）**
```
【访谈第 1 批：范围与读者】已完成代码盘点，初步识别 N 个大功能点、M 个子功能（清单见下）。以下 5 个问题需要你确认，答案将写入「功能清单」与「文档说明」。若某项暂不确定，回复「待定」，我取默认值并标注【待确认】。
```
**模板 2：附选项与默认值**
```
Q4 本文档主要读者是：A 研发；B 研发 + UI + QA；C 含管理层；D 对外客户。默认 B。
```
**模板 3：追问（换角度，不重复原话）**
```
关于 Q13 还需要确认一点：迭代 1 只包含评分标准上传，还是连同评分项配置一起排入？这决定功能清单里「所属迭代」列怎么填。
```
**模板 4：拒答时给出默认值与回退承诺**
```
收到，Q2 版本号按默认 V1.0 处理，PRD 中标注【待确认：版本号】；你确认后我用模式 B（增量更新）只改涉及字段，不重写正文。
```
**模板 5：起草前复述确认**
```
起草前复述关键结论：范围 = A 模块；版本 = V1.0；读者 = 研发 + QA；迭代 = 2 个；上线时间 = 【待确认】。如与预期不符，指出编号即可。
```

话术约束：每个问题只问一件事，禁止双重问题（如把「读者和用途」合并）；禁止使用「是否还有其他需求」这类无信息量提问；不用感叹号与营销措辞。

## 6. 默认策略表

| 缺失信息 | 默认值 | 标注要求 | 回收时机 |
|---|---|---|---|
| 产品/模块名称 | 取仓库 README 或依赖清单中的项目名；无则写【产品名称待确认】 | 文首标题处标【待确认】 | 交付前 |
| 版本号 | V1.0 | 「版本目标」与修订记录标【待确认：版本号】 | 第 1 批访谈 |
| 目标读者 | 研发、UI、QA | 「文档说明」标【待确认】 | 第 1 批访谈 |
| 迭代划分 | 全部大功能点归入「迭代1」，不强行拆分 | 「迭代规划」标【待确认】 | 第 3 批访谈 |
| 迭代时间范围、上线时间 | 不编造日期，直接写【待确认】 | 对应单元格标【待确认】 | 第 3 批访谈 |
| 产品目标量化指标 | 写定性目标并标【待确认：指标值】 | 「产品目标」处 | 交付前 |
| 角色与权限 | 以代码中的角色枚举与鉴权判断为准；无则为单一「普通用户」 | 「使用角色」标【待确认】 | 第 2 批访谈 |
| 设计规范 | 采用 SKILL.md「通用设计机制」的默认值 | 默认机制已声明为默认，不另标【待确认】 | — |
| 测试用例 | 不生成，附件位写「【测试用例待生成：demo 定型后统一生成】」 | 附件位 | 用户指令时 |
| 交付格式 | Markdown 草稿确认后转 Word（见 delivery-guide.md） | 用户提出异议时才标【待确认】 | 第 4 批访谈 |

默认策略的硬约束：**日期、人名、指标数值不得编造**，一律【待确认】；设计规范类默认值可直接采用，因为 SKILL.md 已声明其为可调整默认内容。

## 7. 必须问 vs 可推断

| 信息项 | 判定 | 依据或来源 | 处理方式 |
|---|---|---|---|
| 产品范围、版本号、不做范围 | 必须问 | 代码无法表达发布策略 | 第 1 批 P0 |
| 目标读者与文档用途 | 必须问 | 代码不含读者信息 | 第 1 批 P0 |
| 业务背景、产品目标 | 必须问 | 代码只有实现，没有动机 | 第 2 批 P0 |
| 迭代划分、优先级排序 | 必须问 | 属于组织排期决策 | 第 3 批 P0/P1 |
| 上线时间、验收时间 | 必须问（可待确认） | 代码无法推断 | 第 3 批 P1，禁止编造 |
| 验收标准 | 必须问 | 代码实现不等于验收口径 | 第 4 批 P1 |
| 大功能点与子功能清单 | 可推断（功能盘点） | 路由、导航菜单、页面组件、接口 | 盘点后交用户确认，不逐项提问 |
| 字段、校验与限制条件 | 可推断优先 | 表单校验规则、接口校验、数据约束 | 代码有则直接写；缺失项再问 |
| 角色与权限点 | 部分可推断 | 角色枚举、路由守卫、接口鉴权 | 推断后用 1 个问题确认 |
| 交互状态与视觉样式 | 可推断 | 事件绑定、状态管理、全局样式 | 直接写入「具体说明」 |
| 设计规范与视觉稿 | 部分可推断 | 设计 token、全局样式文件、组件库 | 有则引用，无则用默认机制 |
| 技术架构、部署方式 | 可推断 | 依赖清单、配置文件 | 一般不写入 PRD，涉及时再问 |
| 交付格式偏好 | 必须问（轻量） | 使用场景决定 | 默认 Word，第 4 批复核 |

判定规则：先问「代码仓库里能否找到确定答案」；能则归入可推断并附证据文件位置，不能才进入问题库。若代码证据与用户答复冲突，以用户答复为需求事实，同时把冲突写入记录模板的冲突表。

## 8. 访谈结果记录模板

每批访谈结束后按下列模板记录，核心结论并入 PRD「一、2 文档说明」，同时作为后续「待确认」收回与增量更新的依据。

```markdown
## 访谈记录（第 N 批）

- 时间：yyyy-mm-dd hh:mm:ss
- 对象：【角色；未提供时写「未提供」】
- 本轮问题：Qx–Qy，共 N 条

### 答案记录

| 问题编号 | 问题摘要 | 用户答复要点 | 来源 | 状态 |
|---|---|---|---|---|
| Q1 | 文档范围 | 仅 A 模块，不含 B | 用户口述 | 已确认 |
| Q2 | 版本号 | 暂不确定 | 用户口述 | 【待确认】 |

### 已采用默认值

| 信息项 | 默认值 | 影响章节 |
|---|---|---|
| 版本号 | V1.0 | 文首标题、版本目标、修订记录 |

### 与代码证据冲突项

| 信息项 | 用户答复 | 代码证据（文件:行） | 裁决 |
|---|---|---|---|
| 权限角色数 | 3 类 | 实际枚举 2 类（src/roles.ts:12） | 待用户裁决 |

### 待确认清单

| 序号 | 待确认事项 | 回收时机 | 回收方式 |
|---|---|---|---|
| 1 | 版本号是否 V1.0 | 起草前 | 下批发问 |

### 下一批问题（不超过 5 条）

1. ……
```

## 9. 结束访谈的判定

以下条件全部满足才可进入起草：

1. 范围与版本、读者与用途、业务背景与目标三类 P0 问题均已有答案或明确【待确认】。
2. 功能盘点结果已向用户确认，大功能点与子功能清单无异议。
3. 每个大功能点有归属迭代；无归属者已声明「暂不排期」或标【待确认】。
4. 待确认清单已记录，且不阻塞文档主体结构搭建。
5. 用户已知晓：后续变更通过模式 B（增量更新）处理，不重写未涉及章节。

## 10. 答案落入 PRD 的章节

| 访谈主题 | 落入章节 |
|---|---|
| 范围与版本 | 文首标题、一、5 版本目标、一、9 迭代规划 |
| 读者与用途 | 一、2 文档说明 |
| 业务背景与目标 | 一、1 一句话价值、一、3 业务背景、一、4 产品目标 |
| 角色与权限 | 一、6 使用角色；各子功能「限制条件」 |
| 迭代与排期 | 一、7 功能清单「所属迭代」、一、9 迭代规划、子功能「迭代版本/任务规划」 |
| 设计规范 | 二、通用设计机制（按项目实际情况调整） |
| 验收标准 | 子功能「限制条件」、SKILL.md 第 6 节测试用例与 `references/testcase-spec.md`（按需生成时） |
| 待确认项 | 内联写入正文对应位置，Word 中红色显示（不设附录 A 汇总表） |

## 11. 常见错误与纠正

| 错误 | 后果 | 纠正 |
|---|---|---|
| 一轮抛出 10 个以上问题 | 用户只答前几条，信息残缺 | 拆批，每批不超过 5 条，P0 优先 |
| 问代码里已有的信息 | 浪费提问额度，暴露未做盘点 | 提问前逐条对照第 7 节 |
| 用「是否还有其他需求」收尾 | 得到无信息量答复 | 改问具体缺口，如「B 模块本期是否上线」 |
| 用户拒答后反复追问 | 访谈卡住，用户失去耐心 | 记【待确认】并给默认值，最多再确认 1 次 |
| 把推测写成结论且不标注 | 研发按错误前提开工 | 未确认项一律【待确认】 |
| 只记结论不记来源 | 后期无法追溯与复评 | 使用第 8 节模板，标注来源与状态 |
| 忽略与代码的冲突 | PRD 与实现脱节 | 记录冲突项并请用户裁决 |
