# 质量检查清单（quality-checklist）

> 本文件中的引用路径均相对技能根目录（SKILL.md 所在目录）。

> **何时读取**：SKILL.md 阶段 5「自查与门禁」；交付前必须逐项勾选。可运行脚本时先执行 `scripts/validate_prd.py`，再人工核对本清单。

## 使用方式

1. 逐项核对，通过打 `[x]`，不通过记录问题并修复。
2. 「必须」项任一不通过 = 不可交付；「建议」项不通过 = 记录并在交付说明中注明。
3. 修复后从第一项重新核对，最多 3 轮；仍有必须项不通过时，如实向用户报告剩余问题。

## A. 文档结构（必须）

- [ ] 章节与模板一致：一、产品需求背景 → 二、通用设计机制 → 三、功能详细描述 → 附录 A、待确认清单，无自创、合并、缺漏
- [ ] 一级章节编号「一、二、三」，二级「1、2、3」，三级「1.1、1.2」，编号连续不跳号
- [ ] 标题层级未超过模板规定层级（`##` → `###` → `####` → `#####`）
- [ ] 模板占位符已全部替换：无 `【产品/模块名称】`、`【大功能点名称】`、`xxx`
- [ ] 文档头部有版本号、撰写日期、状态
- [ ] 「文档说明」含用途、目标读者、术语定义、修订记录表
- [ ] 修订记录表至少一行，日期为真实日期（yyyy-mm-dd）

## B. 功能清单与框架图一致性（必须）

- [ ] 第 7 节功能清单为 6 列，每行与第三部分正文一一对应
- [ ] 第 7 节「所属迭代」与功能字段「迭代版本」一致
- [ ] 第 7 节「优先级」与功能字段「优先级」一致
- [ ] 第 8 节框架图层级完整：版本 → 迭代 → 大功能点 → 子功能
- [ ] 框架图中的大功能点/子功能数量、命名与功能清单及正文完全一致，无截断遗漏
- [ ] 框架图无清单之外的功能点（有则提示用户确认后补充）
- [ ] Word 中框架图为图片，无 markmap 代码文本残留

## C. 字段与格式（必须）

- [ ] 每个子功能 9 个字段齐全、顺序正确：标题 / 更新时间 / 优先级 / 迭代版本 / 任务规划 / 功能描述 / 核心流程 / 具体说明 / 限制条件
- [ ] 子功能标题编号在大功能点下顺延，居中加粗
- [ ] 字段标签加粗；各字段独立成行
- [ ] 更新时间格式 `yyyy-mm-dd hh:mm:ss`，与本次实际改动一致
- [ ] 优先级为 P0/P1/P2 且有判定依据，未出现「全部 P0」
- [ ] 任务规划格式 `yyyy-mm-dd——yyyy-mm-dd`
- [ ] 功能描述 ≤150 字，说明使用场景、使用人、解决什么问题
- [ ] 核心流程使用「 → 」串联，每步一个原子动作，包含入口到完成的关键节点
- [ ] 限制条件逐条编号；确无限制时写「无」，未留空
- [ ] 每个子功能均以两列表格呈现，左列有原型图或【原型图待补充】+ 页面元素清单，右列字段完整
- [ ] 每个子功能至少 1 张原型图，未在多个子功能间复用同一张图
- [ ] 未出现「同上」「略」「参见上文」等缩写替代字段

## D. 具体说明深度（必须）

- [ ] 编号格式为 N. / N.M / N.M.K / N.M.K.L，未使用「①」「-」「(1)」等其他形式
- [ ] 缩进逐级为 4 / 8 / 12 空格，同层一致，视觉对齐
- [ ] 同级编号连续，无跳号；每个子功能从 1. 重新开始
- [ ] 一级条目按描述主题分组（入口 / 页面组成 / 校验与提示 / 保存与回显 / 关闭等）
- [ ] 每个叶子条目含至少一项可验证要素（名称 / 位置 / 样式 / 交互结果 / 数据规则 / 限制）
- [ ] 叶子条目达到「无需追问即可执行」，读者不再产生「具体是什么样？点了会怎样？」
- [ ] 按钮类写明交互后效果、作用范围、生效时机三要素
- [ ] 列表类写明字段、超长截断、空数据展示、行内操作所在列、排序、分页、筛选记忆规则
- [ ] 表单类写明控件形式、必填、字数/字符限制、校验时机、提交成功/失败反馈、防重复提交
- [ ] 交互状态（悬停 / 焦点 / 禁用 / 加载中 / 选中）有具体视觉描述，未只写静态布局
- [ ] 操作后的即时反馈明确（刷新整表 / 仅刷新当前行并高亮 / 不刷新）
- [ ] 跳转类写明跳转方式与返回后状态保留规则
- [ ] 异常类写明触发条件、页面表现、提示语、数据是否回滚
- [ ] 权限类写明无权限时的入口隐藏/置灰/拦截方式与提示

## E. 测试用例（生成时必须）

- [ ] 仅对用户指定迭代生成；未生成的迭代附件位为「【测试用例待生成：demo 定型后统一生成】」，未留空
- [ ] 表头固定 8 列，顺序正确
- [ ] 序号在迭代内连续，无跳号
- [ ] 每条用例「关联功能点」编号可在正文中定位
- [ ] 场景类型只使用四类之一；四类场景按需覆盖
- [ ] 每个功能点至少 1 条正常流程用例
- [ ] 「具体说明」每个叶子条目至少被 1 条用例覆盖
- [ ] 「限制条件」每条限制至少 1 条用例验证
- [ ] 边界值给出具体数字，非「超长内容」等模糊表述
- [ ] 预期结果与「具体说明」原文一致，无二次发挥
- [ ] 用例优先级与所属功能点一致
- [ ] 超过 30 条时按场景类型拆 4 张子表，表头重复
- [ ] Word 中为嵌入 Excel 对象，非 Word 原生表格、非截图

## F. 证据与待确认（必须）

- [ ] 每个功能可追溯到功能盘点中的代码证据
- [ ] 无编造的功能、数据、指标、时间、人名
- [ ] 所有【待确认】项已汇总到附录 A，含位置、问题、影响、建议确认人
- [ ] 附录 A 与正文【待确认】标注一一对应，无遗漏、无多余
- [ ] 业务背景与产品目标中无凭空的量化指标；无依据的指标已标【待确认】

## G. 交付格式（必须）

- [ ] 已产出 Markdown 草稿且经用户确认（或用户明确要求直接出 Word）
- [ ] Word 中各级标题与具体说明序号为自动多级编号，非手打数字
- [ ] 复制到钉钉文档后序号仍可自动续排（抽查 1–2 处）
- [ ] 加粗、表格、层级格式在 Word 中完整保留
- [ ] 测试用例为嵌入 Excel，可直接双击编辑
- [ ] 已用探测到的 WPS 可执行文件（完整路径）或系统默认应用打开 .docx，未让用户自行查找；实际使用的应用已写入交付说明
- [ ] 交付说明包含产物路径、遗留【待确认】项、工具降级说明（如有）
- [ ] 文件命名符合 `PRD-{产品/模块}-V{x.y}.docx` 约定（用户指定时从用户）

## H. 语言与风格（必须 / 建议）

- [ ] 中文正式、严谨、无歧义；无口语化表达（必须）
- [ ] 无营销话术（「强大」「一站式」「赋能」）、无感叹号堆砌（必须）
- [ ] 同一概念全文使用同一名称，不混用同义词（必须）
- [ ] 未出现 HTML 转义实体写法（amp、lt、gt、quot 等字符实体；表格内 `<br>` 换行与 `&nbsp;` 缩进除外）；表格换行统一使用 `<br>`（必须）
- [ ] 中英文、数字与中文之间空格统一；标点使用中文全角（建议）
- [ ] 无「待补充」「后续完善」等无主语的遗留措辞，替换为【待确认】或具体内容（建议）

## 判定规则

- 必须项全部通过 → 可交付。
- 任一必须项不通过 → 修复后重新核对，**不得交付**。
- 建议项不通过 → 可交付，但须在交付说明中列出。
- 3 轮修复后仍有必须项不通过 → 向用户如实报告剩余问题与原因，由用户决定是否继续。
