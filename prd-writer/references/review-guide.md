# 评审指南

> **何时读取本文件**：SKILL.md 模式 C「评审」时读取（只读评审、不改写文档）；阶段 5 质量门禁自查完成后需要第二视角独立复核时，同样读取本文件。本文件提供输入物清单、评审流程、六大维度检查点、问题分级、报告模板、结论判定规则、常见问题库与修复流程。 本文件中的引用路径均相对技能根目录（SKILL.md 所在目录）。

## 目录

1 定位与边界；2 输入物与前置条件；3 评审流程；4 六大评审维度（4.1–4.6）；5 问题分级；6 报告模板；7 结论判定；8 常见问题库；9 修复流程；10 复评与关闭；11 与质量门禁的关系。

## 1. 评审模式的定位与边界

- 评审模式（模式 C）只做三件事：发现问题、给出证据、给出可执行的修改建议；**不直接修改文档**。
- 评审输出是独立报告，不是重写后的 PRD。需要修改时，经用户确认后转入模式 B（增量更新，只改问题项涉及的小节）。
- 评审以 SKILL.md 的模板、字段规范、质量门禁与语言规范为依据；不以评审者个人偏好为依据。
- 评审必须可追溯：每条问题要有文档位置与证据；无法验证的内容标注「评审范围限制」，不得凭直觉判定。
- 评审不替代生成后的自查：自检未通过不得提交评审。

## 2. 输入物与前置条件

| 输入物 | 必要性 | 缺失时的处理 |
|---|---|---|
| 待评审 PRD（Markdown 或 .docx） | 必须 | 无法评审，要求用户提供文件路径 |
| SKILL.md（评审依据） | 必须 | 从技能目录读取；版本不一致时在报告中注明依据版本 |
| 功能盘点.md（证据底稿） | 建议 | 缺失时「证据支撑」维度只能抽查代码，无法核对盘点与正文是否一致 |
| 代码仓库或代码快照 | 强烈建议 | 缺失时「证据支撑」维度降级，在报告中声明评审范围限制 |
| 访谈记录或待确认清单 | 建议 | 缺失时对「【待确认】应覆盖哪些信息」只做抽样判断 |
| 项目设计规范或视觉稿 | 可选 | 用 SKILL.md 通用设计机制作为基准 |
| 历史评审报告 | 可选 | 无则不对比历史问题趋势 |

前置检查：确认 PRD 版本号与更新时间（以文件内记录为准，不以文件修改时间为准）；确认代码仓库路径与分支；若文档为 .docx，先转为 Markdown 文本再逐项检查，避免漏检表格与编号。

## 3. 评审流程（六步）

1. **读取与版本确认**：读取 PRD 全文，记录版本号、更新时间、章节数、大功能点与子功能数量。
2. **结构扫描**：按模板核对章节完整性、标题层级、表格结构；先找出结构性缺陷，避免后续逐条检查被大量格式问题干扰。
3. **逐维度检查**：按第 4 节六个维度依次检查，每个维度记录候选问题与文档位置。
4. **证据核验**：把「证据支撑」类问题回到代码中核实（文件、组件、路由、接口、校验规则），确认是文档错误而非代码遗漏；核实不了的转为建议或标注待验证。
5. **分级与结论**：按第 5 节分级、按第 7 节判定结论；同一问题的多处出现合并为一条，在「文档位置」列列出所有位置。
6. **报告输出**：按第 6 节模板输出报告，问题按严重级别排序（阻塞 → 重要 → 建议），同级按文档顺序排列。

评审顺序的硬规则：先结构后细节、先阻塞后建议、先证据后措辞。禁止跳过结构扫描直接逐句润色。

## 4. 六大评审维度与检查点

### 4.1 完整性

| 检查点 | 判定依据 | 常见缺陷 |
|---|---|---|
| 模板章节齐全 | 含「一、产品需求背景」9 个小节、「二、通用设计机制」、「三、功能详细描述」，有【待确认】时含附录 A | 缺版本目标、缺功能框架图、缺迭代规划 |
| 功能清单与正文一一对应 | 清单每行都能在正文找到对应大功能点与子功能 | 清单多列或漏列 |
| 子功能字段集齐全 | 标题、更新时间、优先级、迭代版本、任务规划、功能描述、核心流程、具体说明、限制条件 | 缺核心流程、限制条件留空 |
| 两列表格呈现 | 每个大功能点下为「原型展示图｜功能描述」两列多行表格 | 用普通段落描述、表格列错位 |
| 原型图占位齐全 | 每个子功能至少 1 张截图或【原型图待补充：页面名称】 | 整列留空、多子功能共用一张图 |
| 功能框架图完整 | 层级为版本 → 迭代 → 大功能点 → 子功能，无截断 | 遗漏迭代、分支被截断 |
| 非功能需求完整 | 至少覆盖性能、可用性、兼容性三项 | 只有功能描述 |

### 4.2 一致性

| 检查点 | 判定依据 | 常见缺陷 |
|---|---|---|
| 三处清单一致 | 功能清单、功能框架图、正文的大功能点与子功能数量、命名完全一致 | 某处改名或漏项 |
| 编号连续 | 子功能编号在大功能点下顺延；「具体说明」为 N. / N.M / N.M.K / N.M.K.L，无跳号 | 1.1、1.3 跳号；编号格式混用 |
| 迭代归属一致 | 功能清单「所属迭代」= 正文「迭代版本」= 框架图所在分支 | 一处写迭代1、一处写迭代2 |
| 优先级一致 | 功能清单、子功能字段、用例优先级同一功能点一致 | 正文 P0、用例 P2 |
| 术语统一 | 大功能点、子功能、具体说明、限制条件、迭代、功能盘点、质量门禁、【待确认】 | 混用「功能点」「模块」「说明」 |
| 字段标签统一 | 标签文字、加粗、冒号与模板一致 | 「功能描述」写成「描述」 |
| 交叉引用有效 | 「见第 X 节」「编号 1.2-2.2.1」指向的对象存在 | 引用已删除的章节 |
| 版本与日期一致 | 文首版本号、版本目标、修订记录、迭代规划日期口径一致 | 修订记录版本号落后 |

### 4.3 可执行性

| 检查点 | 判定依据 | 常见缺陷 |
|---|---|---|
| 叶子条目可执行 | 阅读后可直接估算工时、绘制界面、编写用例 | 只有页面布局描述 |
| 交互三要素齐全 | 交互后效果、作用范围、生效时机 | 只写「点击后保存」 |
| 分类信息齐全 | 按钮、列表、提示、资源、数据、布局、异常、交互状态、跳转、表单提交类按规范写全 | 列表缺空状态与排序规则 |
| 列表类完整 | 字段、空状态、行内操作所在列、排序、筛选记忆、分页 | 只写字段清单 |
| 核心流程可用 | 用「 → 」串联原子动作，分支在主线后补充 | 流程缺入口或中间跳转 |
| 限制条件可判定 | 每条限制可判断成立与否；无限制写「无」 | 写「视情况而定」 |
| 无不可执行表述 | 不出现「适当提示」「优化体验」「合理展示」 | 大量模糊动词 |

### 4.4 可测性

| 检查点 | 判定依据 | 常见缺陷 |
|---|---|---|
| 叶子条目可验证 | 每条含名称、位置、样式、交互结果、数据规则、限制中的至少一项 | 纯主观描述 |
| 边界值具体 | 字数、大小、次数、时间边界给出具体数字 | 只写「输入超长内容」 |
| 异常与权限覆盖 | 「具体说明」含异常类条目；角色差异写入限制条件 | 只写正常流程 |
| 用例覆盖 | 每个大功能点至少 1 条正常流程；叶子条目全覆盖；限制条件全覆盖；未生成时附件位有「待生成」标注 | 用例与正文脱节、附件位空白 |
| 用例表规范 | 8 列齐全，场景类型仅四类，序号连续，关联功能点编号可追溯 | 缺前置条件、预期结果笼统 |
| 预期结果一致 | 提示语、颜色、淡出时间与「具体说明」原文一致 | 二次发挥 |

### 4.5 证据支撑

| 检查点 | 判定依据 | 常见缺陷 |
|---|---|---|
| 功能有代码依据 | 大功能点、子功能可在路由、菜单、页面组件、接口中找到 | 凭空新增功能 |
| 字段与规则真实 | 字段名、校验规则、枚举值、数据格式与代码一致 | 编造字段与接口 |
| 角色与权限真实 | 角色清单、权限点与代码枚举、鉴权逻辑一致 | 多写不存在的角色 |
| 需求事实有来源 | 范围、版本、迭代、目标来自访谈记录或用户确认 | 用推测填充业务背景 |
| 原型图有来源 | 截图来自 demo 或明确标注待补充 | 使用无关截图 |
| 数据示例合规 | 日期 yyyy-mm-dd hh:mm:ss、金额 2 位小数、百分比整数 | 格式混用 |

### 4.6 语言规范

| 检查点 | 判定依据 | 常见缺陷 |
|---|---|---|
| 正式严谨 | 无口语、无营销话术、无感叹号 | 出现「超级好用」类表述 |
| 无歧义 | 不用「可能」「大概」「适当」「若干」「等等」 | 用模糊词替代具体规则 |
| 无占位残留 | 无 xxx、TODO、待填、未替换的示例值 | 示例值留在正文 |
| 换行标签正确 | 表格单元格内需要换行时使用换行标签，不出现转义实体 | 出现 HTML 实体或直接断行导致表格断裂 |
| 表格完整 | 每行列数与表头一致，分隔行完整 | 竖线数量不一致 |
| 标题层级正确 | 与模板层级一致，无自创层级 | 用加粗文本代替标题 |

## 5. 问题分级定义

| 级别 | 定义 | 判定要点 | 处理要求 |
|---|---|---|---|
| 阻塞 | 文档无法指导研发、UI、QA 执行，或与事实冲突、违反模板强制规范 | 缺章节或必填字段、清单一处不一致、编号断裂、编造功能或数据、原型图整列缺失、用例覆盖缺失 | 必须修复；未清零则结论不得为通过或有条件通过 |
| 重要 | 影响准确性或执行效率，但存在临时绕行方式 | 交互三要素缺项、列表类信息缺失、术语不统一、限制条件不可判定、证据不足、更新时间未更新 | 列入整改条件，限期修复并复评 |
| 建议 | 影响阅读体验、格式美观、表述简洁 | 措辞冗余、表格对齐、示例补充、排序优化 | 记录即可，不阻塞交付 |

分级规则：

- 同一问题出现在多处时合并为一条，严重级别按最严重位置定级，位置全部列出。
- 涉伪造证据（文档描述在代码中完全不存在）一律按阻塞处理，不因影响范围小而降级。
- 不因问题数量多而降级，也不因用户催促而升级；无法验证的问题不列为阻塞，转列「待验证」并在报告中说明限制。

## 6. 评审报告模板

```markdown
# PRD 评审报告

## 一、基本信息

| 项目 | 内容 |
|---|---|
| 评审对象与版本 | 〈PRD 文件路径〉，V1.0，更新时间 yyyy-mm-dd hh:mm:ss |
| 评审模式 | 模式 C（只读评审） |
| 评审依据 | SKILL.md 第 7 节质量门禁（G1–G9）、templates/prd-template.md、references/quality-checklist.md |
| 代码证据范围 | 〈仓库路径、分支、commit〉 |
| 评审时间 | yyyy-mm-dd hh:mm:ss |

## 二、结论

- 结论：通过 / 有条件通过 / 不通过
- 问题统计：阻塞 N 项、重要 N 项、建议 N 项
- 评审范围限制：〈无 / 缺少代码仓库，证据支撑维度仅做抽样〉

## 三、问题清单

| 序号 | 文档位置 | 问题类型 | 严重级别 | 问题描述 | 证据或依据 | 修改建议 |
|---|---|---|---|---|---|---|
| 1 | 三、1、1、1.2 子功能「限制条件」 | 完整性 | 阻塞 | 限制条件字段缺失 | SKILL.md 字段集第 9 项 | 补充限制条件；无限制写「无」 |

## 四、通过条件（有条件通过时填写）

| 序号 | 条件 | 对应问题编号 | 责任方 | 期限 |
|---|---|---|---|---|
| 1 | 补齐 1.2 子功能的限制条件 | 1 | 文档撰写方 | yyyy-mm-dd |

## 五、复评记录

| 复评时间 | 已修复 | 未修复 | 新增 | 复评结论 |
|---|---|---|---|---|
| yyyy-mm-dd hh:mm:ss | 1 | 0 | 0 | 通过 |
```

问题清单填写要求：

- 「文档位置」精确到章节号与子功能编号，如「三、1、1、1.2 子功能『具体说明』第 2 条」。
- 「问题类型」只能取六大维度名称之一：完整性、一致性、可执行性、可测性、证据支撑、语言规范。
- 「证据或依据」写规范条款、代码文件与行号、或原文引用，禁止只写「感觉不对」。
- 「修改建议」必须可执行，写清改哪里、改成什么，不写「建议优化」。
- 同类问题超过 5 条时，合并为一条并列出全部位置，保持报告可读。

## 7. 结论判定规则

| 结论 | 判定条件 | 后续动作 |
|---|---|---|
| 通过 | 阻塞 0 项且重要 0 项（建议项可保留） | 交付说明中列出建议项，进入交付 |
| 有条件通过 | 阻塞 0 项且重要 1–4 项 | 列出通过条件、责任方与期限；修复后复评 |
| 不通过 | 阻塞 ≥1 项，或重要 ≥5 项 | 出具问题清单，转入模式 B（增量更新）修复后重评 |

判定细则：

- 评审范围受限（如无代码仓库）时，最高结论为「有条件通过」，并在报告中声明限制。
- 「有条件通过」的通过条件必须逐条对应问题编号，不得使用「进一步完善文档」这类笼统条件。
- 存在伪造证据类问题，或用户已确认的需求事实被文档改写，直接判「不通过」。
- 结论一经判定不得因交付时间压力更改；用户可要求降低修复范围，但报告须保留原始结论与用户决策记录。

## 8. 常见问题库

| 编号 | 问题类型 | 典型表现 | 严重级别 | 修改方向 |
|---|---|---|---|---|
| C-01 | 完整性 | 缺少「二、通用设计机制」或未声明采用项目已有规范 | 阻塞 | 补章节或写明项目规范出处 |
| C-02 | 完整性 | 子功能缺「限制条件」，或字段留空未写「无」 | 阻塞 | 按字段集补齐 |
| C-03 | 完整性 | 功能框架图漏掉某迭代或大功能点 | 阻塞 | 按功能清单补齐并核对数量 |
| C-04 | 完整性 | 非功能需求缺失（性能、可用性、兼容性） | 重要 | 补指标、可用性要求、兼容矩阵 |
| C-05 | 一致性 | 功能清单 12 个大功能点，正文只写 10 个 | 阻塞 | 三处对齐，以盘点结果为准 |
| C-06 | 一致性 | 子功能编号 1.1、1.3 跳号，或「具体说明」层级编号混用 | 阻塞 | 按规则重排编号 |
| C-07 | 一致性 | 功能清单「所属迭代」与正文「迭代版本」不一致 | 阻塞 | 以迭代规划为准统一 |
| C-08 | 一致性 | 功能清单、框架图、正文三处命名不一致 | 重要 | 统一命名并复核三处 |
| C-09 | 一致性 | 术语混用「功能点/大功能点」「说明/具体说明」 | 建议 | 按术语表统一 |
| C-10 | 可执行性 | 「具体说明」只有页面布局，没有交互反馈 | 阻塞 | 补交互后效果、作用范围、生效时机 |
| C-11 | 可执行性 | 按钮条目缺作用范围与生效时机 | 重要 | 补范围（当前行/选中项/全部）与时机 |
| C-12 | 可执行性 | 列表缺空状态、默认排序、分页、筛选记忆规则 | 重要 | 按列表类要求逐项补 |
| C-13 | 可执行性 | 出现「适当提示」「优化体验」等不可执行表述 | 重要 | 改为具体文案、位置与数值 |
| C-14 | 可测性 | 边界值写「输入超长内容」，无具体数字 | 重要 | 给出具体字数、大小、次数 |
| C-15 | 可测性 | 用例未覆盖「限制条件」中的条目 | 阻塞 | 补用例并做双向核对 |
| C-16 | 可测性 | 未生成用例但附件位空白 | 重要 | 写「【测试用例待生成：demo 定型后统一生成】」 |
| C-17 | 证据支撑 | 描述了代码中不存在的字段、接口或角色 | 阻塞 | 删除或改标【待确认】并回问用户 |
| C-18 | 证据支撑 | 原型图与子功能界面不对应，或多子功能共用一张图 | 重要 | 重新截取对应界面 |
| C-19 | 证据支撑 | 业务目标、迭代时间等需求事实无来源 | 重要 | 引用访谈记录或标【待确认】 |
| C-20 | 语言规范 | 出现 HTML 转义实体、表格竖线数量不一致 | 重要 | 改为普通字符与换行标签，补齐列 |
| C-21 | 语言规范 | 口语化、营销话术、感叹号 | 建议 | 改写为陈述句 |
| C-22 | 语言规范 | 「更新时间」为模板占位或未随改动更新 | 重要 | 更新为实际操作时间 |

## 9. 修复流程（走增量更新模式）

1. **用户确认**：确认评审结论、修复范围（全部问题 / 仅阻塞 / 指定编号）与是否复评。
2. **切换模式**：转入模式 B（增量更新），只改问题项涉及的小节，不重写未涉及章节，不重跑全量生成。
3. **按级修复**：阻塞 → 重要 → 建议；同一章节的多条问题合并处理，减少反复改动。
4. **同步联动**：字段级修复只更新对应子功能「更新时间」；涉及大功能点或子功能增删时，同步更新功能清单、功能框架图与测试用例。
5. **输出修复清单**：逐条给出问题编号、修改内容、修改位置，交用户确认。
6. **触发复评**：只复核已修复项及其关联影响（清单、编号、框架图、用例覆盖），不重跑全量评审。
7. **更新报告**：在评审报告「复评记录」追加一行，给出最终结论。

修复禁止事项：

- 不得通过删除功能点或降低「具体说明」详尽度来消除问题。
- 不得为通过评审而伪造代码证据或篡改评审记录。
- 不得修改用户已确认的需求事实；确需变更时先回问用户。

## 10. 复评与关闭

- 复评触发与范围：修复清单交付后或用户要求复核时执行，只查已修复问题 + 关联影响；修复引入的新问题按正常分级补充。
- 关闭条件：阻塞为 0，且重要为 0 或已全部转为用户认可的整改条件。
- 遗留问题：无法在本期修复的建议项与待确认项，登记在报告末尾，随 PRD 交付说明一并告知用户。
- 报告归档：评审报告默认作为交付物交用户，不写入技能仓库；如需落盘，放在被评审 PRD 同目录的 `review/` 下，命名 `PRD评审报告-〈模块名〉-〈yyyy-mm-dd〉.md`。

## 11. 与质量门禁的关系

| 环节 | 执行者 | 时机 | 不通过的后果 |
|---|---|---|---|
| 质量门禁（自检） | 生成 PRD 的同一代理 | 阶段 5，每次生成或增量更新后、交付前；逐项过 `references/quality-checklist.md` | 不得提交评审或交付，先修复 |
| 评审（模式 C） | 独立第二视角（用户或评审代理） | 自检通过后、交付前 | 按结论修复或重评 |

质量门禁与评审使用同一套依据，但检查深度不同：自检是覆盖式核对（逐条走 `references/quality-checklist.md` 与 SKILL.md 第 7 节 G1–G9），评审是抽样加证据核验（重点查结构、一致性、证据与可测性）。两者结论不一致时，以评审结论为准并记录差异原因。
