# PRD 撰写技能（prd-writer）

把「代码里已经实现的产品事实」翻译成「研发可估时、UI 可出图、QA 可写用例」的产品需求文档。

## 0. 技能定位

### 0.1 适用与不适用

| 适用 | 不适用 |
|------|--------|
| 已有代码仓库（含 demo、原型、生产系统），需要补写 / 补全 PRD | 从零构思新产品，仓库里没有可参考的实现 |
| 按版本、迭代梳理功能清单，规划研发排期 | 纯市场方案、商业计划书、竞品分析 |
| 评审已有 PRD 是否完整、可执行、可测试 | 需要编造数据、指标、人名、时间的文档 |
| 代码变更后同步更新 PRD 对应章节 | 没有代码证据、仅凭口头描述就想定稿的需求 |

### 0.2 三条底线（任何模式下都不可突破）

1. **证据优先**：功能必须能在代码中找到依据（路由、页面、接口、数据模型、权限配置等），找不到依据的内容一律标注【待确认】，禁止编造。
2. **结构固定**：严格遵循 `templates/prd-template.md` 的章节与编号，禁止自创层级、合并或删减章节。
3. **写到可执行**：「具体说明」必须细化到 RD 可估时、UI 可出图、QA 可写用例；读者不再产生「具体是什么样？点了会怎样？」的疑问。

## 1. 模式判定

先判断用户要做哪一种事，再按对应模式执行。用户没有说明时默认**模式 A**；无法判断时只问一句模式问题，不得阻塞等待。

| 模式 | 用户说法示例 | 输入 | 主要输出 | 可跳过的阶段 |
|------|--------------|------|----------|--------------|
| A 完整生成 | 「给这个仓库补个 PRD」「生成 V1.0 需求文档」 | 代码仓库 | 功能盘点 + 完整 PRD（Markdown→Word） | 无 |
| B 增量更新 | 「仅更新 1.2 的限制条件，其他不变」 | 已有 PRD + 代码 | 变更小节 + 修订记录 | 阶段 0、阶段 2 中无关问题 |
| C 评审 | 「评审这份 PRD」「看看还缺什么」 | 已有 PRD（可选代码） | 评审报告（问题表 + 结论） | 阶段 3、4 |
| D 仅功能盘点 | 「先梳理功能点，不要写正文」 | 代码仓库 | `功能盘点.md` | 阶段 3–6 |
| E 测试用例 | 「生成迭代 1 的测试用例」 | 已有 PRD 正文 | 测试用例表（嵌入 Excel） | 阶段 0–3 |

多模式可以组合：例如「先盘点功能点，确认后再写 PRD」= D → A；「写完 PRD 顺手评审」= A → C。一次只推进一个模式，完成一个再进入下一个。

## 2. 工作流（阶段 0–6）

按顺序执行，阶段可合并但**不可跳过**（跳过的前提见模式表）。每个阶段都有明确产物与完成判据，完成判据不满足不得进入下一阶段。

| 阶段 | 目标 | 关键动作 | 产物 | 完成判据 |
|------|------|----------|------|----------|
| 0 范围确认 | 圈定文档边界 | 读仓库 README 与构建配置，识别技术栈、模块、版本；问 ≤3 个阻塞性问题 | 一段「范围摘要」 | 能说清「写哪个产品/模块、版本号、目标读者」 |
| 1 功能盘点 | 把代码翻译成功能清单 | 按 `references/code-analysis-guide.md` 扫描路由/菜单/页面/接口/数据模型/权限，逐条登记代码证据与置信度 | `功能盘点.md` | 每个子功能有代码证据；低置信度项已标【待确认】 |
| 2 访谈补全 | 补代码里拿不到的信息 | 按 `references/interview-guide.md` 的 P0→P1 顺序提问，一次 ≤5 个；能从代码推断的不得问 | 访谈记录（并入 PRD「文档说明」） | P0 问题有答案或明确默认值 |
| 3 骨架确认 | 与用户对齐结构 | 提交功能清单、迭代划分、功能框架图草图、版本目标，请用户确认 | 确认后的功能清单与迭代规划 | 用户确认或明确表示「直接生成」 |
| 4 分迭代起草 | 产出 PRD 正文 | 读取 `templates/prd-template.md` 与 `references/field-spec.md`，逐迭代起草；输出过长时按迭代分段 | PRD Markdown 草稿 | 每迭代章节结构完整、字段齐全 |
| 5 自查与门禁 | 交付前兜底 | 逐项过「7. 质量门禁」；可运行时执行 `scripts/validate_prd.py`；修复循环 ≤3 轮 | 自检通过记录 | 全部门禁项通过（或剩余问题已如实告知用户） |
| 6 交付 | 转成交付物 | 按 `references/delivery-guide.md` 转 Word、渲染框架图、嵌入测试用例 Excel、自动打开 WPS | `.docx` + `.md` | 用户能直接打开 .docx 且格式完整 |

### 2.1 阶段 0：范围确认

读取仓库 README 与构建配置（`package.json` / `pom.xml` / `go.mod` / `pyproject.toml` 等），识别项目类型与模块划分。只问三个阻塞性问题：覆盖范围与版本号、目标读者与用途、迭代如何划分；用户答不上来时给默认值并标【待确认】，继续推进，不要卡在提问上。

### 2.2 阶段 1：功能盘点（核心阶段）

必须产出独立的 `功能盘点.md`（模板见 `references/code-analysis-guide.md`），它是 PRD 的依据，也是与用户对齐功能范围的抓手。

- 扫描顺序：README/文档 → 构建配置 → 路由/菜单/权限 → 页面与组件 → 接口定义 → 数据模型 → 状态管理与文案 → 定时任务/消息/导出等旁路能力。
- 每条功能登记：功能模块、大功能点、子功能、代码证据（`文件路径:行号` 或符号名）、置信度（高/中/低）、建议迭代、备注。
- 置信度：路由 + 页面 + 接口齐全 = 高；仅有路由或菜单 = 中；仅凭代码片段推测 = 低。**低置信度一律进【待确认】**。
- 只记录「用户可感知的产品功能」，不把技术实现当成需求（「列表用 useEffect 监听筛选」应写成「切换筛选条件后列表即时刷新」）。
- 盘点完成后向用户展示功能清单表格，请其增删改；确认后再进入起草。

### 2.3 阶段 2：访谈补全

按 `references/interview-guide.md` 执行：一轮最多 5 个问题，优先 P0；能从代码推断的信息不得提问；回答直接写入对应章节，未回答且影响交付的项标【待确认】并进入附录 A。

### 2.4 阶段 3：骨架确认

向用户提交功能清单（模板 一、7）、迭代规划（模板 一、9）、功能框架图草图（模板 一、8）、版本目标（模板 一、5），等待一轮确认后写正文；用户明确说「直接生成」的，按当前盘点结果生成并在交付时说明假设。

### 2.5 阶段 4：分迭代起草

起草前**必须**读取 `templates/prd-template.md` 与 `references/field-spec.md`；写测试用例前读取 `references/testcase-spec.md`。以「迭代」为最小完整单元输出，每完成一个迭代做一次局部自查；输出超长时按「4.8 输出长度管理」分段，禁止在句子、表格或字段中间截断；原型图按「4.9 原型图规则」处理。

### 2.6 阶段 5：自查与门禁

逐项执行「7. 质量门禁」。能运行脚本时先跑 `python scripts/validate_prd.py <PRD Markdown 文件>`（路径相对技能根目录），按报告修复后重跑；脚本不可用时手工逐项核对。修复循环最多 3 轮，仍有未通过项时在交付说明中如实列出，禁止隐瞒。

### 2.7 阶段 6：交付

按 `references/delivery-guide.md` 执行：Markdown 定稿 → 转 Word → 功能框架图渲染为 PNG 插入 → 测试用例以嵌入 Excel 对象插入 → 自动打开 → 向用户说明产物路径与遗留的【待确认】项。任一环节工具不可用时，明确告知用户并给出可执行的替代步骤，不得静默降级。

## 3. 模式细则

### 3.1 模式 A：完整生成

按阶段 0 → 6 全流程执行。交付物：`功能盘点.md`、`PRD-{产品/模块}-V{版本}.md`、`PRD-{产品/模块}-V{版本}.docx`。

### 3.2 模式 B：增量更新

1. 只读取本次调整涉及的章节与对应代码，跳过无关访谈。
2. 不重写未涉及的章节与小节，只输出变更后的完整小节（便于用户整体替换）。
3. 仅当调整涉及**功能点增删**时，才同步更新模板 一、7 功能清单与 一、8 功能框架图；字段级调整不触发这两处更新。
4. 「更新时间」只更新被修改的功能，不做全文批量刷新；同时在「文档说明」的修订记录表追加一行（版本 / 日期 / 修改人 / 变更内容）。
5. 若变更了「具体说明」或「限制条件」，对应迭代的测试用例须同步更新；暂不更新时在附件位标注【测试用例待重新生成】。
6. 输出变更说明：改了哪些位置、为什么改、是否影响功能清单与框架图。

### 3.3 模式 C：评审

按 `references/review-guide.md` 执行。输出评审报告而非直接改文档：问题表（序号 / 文档位置 / 问题类型 / 严重级别 / 问题描述 / 证据或依据 / 修改建议）+ 结论（通过 / 有条件通过 / 不通过）+ 统计。用户要求修复时，转为模式 B 逐条修复。

### 3.4 模式 D：仅功能盘点

只执行阶段 0–2，输出 `功能盘点.md` 与功能清单概览表，不写 PRD 正文、不转 Word。结尾给出「建议迭代划分」与「待确认清单」。

### 3.5 模式 E：测试用例

按 `references/testcase-spec.md` 执行。可指定迭代；未指定时默认最近一个迭代。生成后在 Word 中以嵌入 Excel 对象呈现，不得用 Word 原生表格或截图代替。

## 4. 全局输出规范（硬性）

### 4.1 语言与风格

中文，正式、严谨、无歧义。杜绝口语化表达、营销话术、感叹号堆砌。同一概念全文使用同一名称；使用产品语言描述行为，不直接使用代码标识符（确需说明时可写作「用户列表（UserList）」）。

### 4.2 格式与编号

Markdown。标题层级与编号严格遵循模板：一、二、三 → 1、2、3 → 1.1、1.2。「具体说明」编号为 N. / N.M / N.M.K / N.M.K.L，禁止其他形式。表格不得缺列、不得用空行截断。

### 4.3 不确定信息

一律标注【待确认】，禁止编造数据、时间、人名、指标。所有【待确认】项汇总到文末「附录 A、待确认清单」，写明位置、问题、影响、建议确认人。

### 4.4 更新时间

格式 `yyyy-mm-dd hh:mm:ss`（24 小时制）。任何内容发生改动时，同步更新该功能条目的「更新时间」；全文结构级调整时追加修订记录。不要为了「看起来新」而批量刷新无关条目的时间。

### 4.5 代码证据与追溯

每个功能点在 `功能盘点.md` 中必须可追溯到代码位置（文件路径 + 行号或符号名）。PRD 正文以产品语言呈现，不暴露代码路径；证据保存在功能盘点中，便于评审核对。无法追溯的功能一律进【待确认】。

### 4.6 交付格式

最终交付物为 Word 文档（`.docx`）。流程：先产出 Markdown 草稿并经用户确认，再转换为 Word；转换后标题层级、编号、加粗等格式须完整保留。各级标题与「具体说明」条目序号在 Word 中必须使用**自动多级编号**（不得手打数字文本），使全文复制到钉钉文档后序号仍可自动续排（交付前按 `references/delivery-guide.md` 实测一次）。测试用例部分**不以 Word 原生表格或 Markdown 表格交付**，须以嵌入的 Excel 对象（Embedded Microsoft Excel Worksheet）插入对应位置，保留 8 列表头与排序规则，使 QA 可直接在 Word 内双击编辑、筛选、导出。**每次生成完成后，必须立即用 WPS 打开该 .docx**：先探测本机 WPS 可执行文件（不要假设 `wps` 在 PATH 中），探测不到时用系统默认应用或 Word 打开，并在交付说明中写明实际使用的应用。

### 4.7 功能框架图

PRD 必须包含「功能框架图」小节。Markdown 草稿阶段以 markmap 代码块作为数据源；转 Word 时将思维导图渲染为 PNG 插入对应位置、替代代码块，最终 Word 中不得以代码文本形式呈现。**生成完成后必须核对框架图完整性**：大功能点与子功能的数量、命名须与模板 一、7 功能清单及 三、功能详细描述正文完全一致，不得遗漏、不得截断；发现清单之外的功能点时，提示用户确认后补充。

### 4.8 输出长度管理

生成前按功能点数量估算输出长度。预估超出单次输出上限时，主动分段生成：每段以一个迭代（或一个大功能点）为完整单元，段尾标注「（第 N/N 段完，回复『继续』生成下一段）」。分段优先选择迭代边界，其次是大功能点边界；每段必须结构完整、可独立保存；**禁止在句子、表格或字段中间截断**。

### 4.9 原型图规则

- 左列「原型展示图」优先使用项目 demo/原型页面的真实截图，每个子功能至少 1 张，禁止同一张图复用于多个子功能。
- 可启动本地 demo 时，按页面实际状态截图；无法获取截图时写【原型图待补充：〈页面/弹窗名称〉】，并在该单元格补充「页面元素清单」（标题、区域、按钮、字段），保证 UI 可据此出图。
- 禁止留空，禁止用占位色块代替说明。

### 4.10 文件命名与目录

| 产物 | 命名 | 建议位置 |
|------|------|----------|
| 功能盘点 | `功能盘点-{产品/模块}.md` | `docs/prd/` |
| PRD 草稿 | `PRD-{产品/模块}-V{x.y}.md` | `docs/prd/` |
| PRD 交付 | `PRD-{产品/模块}-V{x.y}.docx` | `docs/prd/` |
| 测试用例附件 | 由交付工具内嵌，不单独命名 | 嵌入 PRD Word 内 |

用户指定路径时以用户为准。

## 5. 模板与字段规范

### 5.1 文档骨架（固定，不可增删章节）

| 章节 | 内容 | 强制 |
|------|------|------|
| 一、产品需求背景 | 一句话价值 / 文档说明（含修订记录、术语）/ 业务背景 / 产品目标 / 版本目标 / 使用角色 / 功能清单 / 功能框架图 / 迭代规划 | 是 |
| 二、通用设计机制 | 页面风格、弹窗、提示语、表格、按钮、表单、空状态与加载、异常处理、数据格式、非功能需求 | 是（按项目调整） |
| 三、功能详细描述 | 版本 → 迭代 → 大功能点 → 子功能，两列表格逐行呈现 | 是 |
| 附录 A、待确认清单 | 位置 / 待确认问题 / 影响 / 建议确认人 | 是（有【待确认】时） |

### 5.2 功能点字段集（每个子功能必须齐全且顺序固定）

1. 功能点标题（子功能编号在大功能点下顺延，居中、加粗）
2. 更新时间（`yyyy-mm-dd hh:mm:ss`）
3. 优先级（红色加粗；P0 = 阻塞主流程/核心合规，P1 = 重要但不阻塞，P2 = 体验优化）
4. 迭代版本（如「迭代1」）
5. 任务规划（`yyyy-mm-dd——yyyy-mm-dd`）
6. 功能描述（≤150 字，说明使用场景、使用人、解决什么问题）
7. 核心流程（用「 → 」串联原子动作；有分支时在主线后分条补充）
8. 具体说明（穷尽式细化，编号与缩进规则见 `references/field-spec.md`）
9. 限制条件（权限、次数上限、前置条件、环境要求；无则写「无」）

### 5.3 「具体说明」最低标准

- 按用户使用路径或逻辑维度分组（入口、页面组成、校验与提示、保存与回显、关闭等），逐级拆到原子粒度（单个按钮、单个字段、单个状态、单条提示）。
- 每个叶子条目至少含一项可验证要素：名称、位置、样式、交互结果、数据规则或限制。
- 凡涉及用户操作的组件写清三要素：**交互后效果**（页面反馈 + 数据变化）、**作用范围**（当前行/选中项/查询结果/全部数据，影响哪些关联数据）、**生效时机**（立即 / 二次确认后 / 保存后生效）。
- 交互状态（悬停、焦点、禁用、加载中、选中）与操作后的即时反馈（刷新整表 / 仅刷新当前行并高亮 / 不刷新）必须写明，禁止只写静态布局。
- 完整范例与反例见 `references/field-spec.md`。

## 6. 测试用例（按需生成）

- demo 未定型阶段默认**不生成**测试用例，各迭代附件位写「【测试用例待生成：demo 定型后统一生成】」；用户明确指令「生成测试用例」后再按规范生成。
- 固定 8 列：序号｜关联功能点｜用例名称｜场景类型｜前置条件｜测试步骤｜预期结果｜优先级。
- 四类场景：正常流程 / 异常操作 / 边界条件 / 权限校验；优先级与所属功能点一致。
- 覆盖要求：「具体说明」每个叶子条目至少被 1 条用例覆盖；「限制条件」每条至少 1 条用例验证；每个功能点至少 1 条正常流程用例。
- 单个迭代超过 30 条时按场景类型拆 4 张子表；30 条以内用一张表。
- Word 中必须以嵌入 Excel 对象交付。完整规范见 `references/testcase-spec.md`。

## 7. 质量门禁（输出前必须逐项通过）

| 编号 | 门禁项 | 通过标准 | 检查方式 |
|------|--------|----------|----------|
| G1 | 结构完整 | 章节齐全、编号与模板一致，无自创层级 | 对照 `templates/prd-template.md` |
| G2 | 功能一致 | 模板 一、7 功能清单、一、8 功能框架图、三、功能详细描述正文三处功能数量与命名完全一致 | 三方逐一比对 |
| G3 | 字段齐全 | 每个子功能 9 个字段齐全、顺序正确、无空字段 | 逐功能核对 |
| G4 | 编号规范 | 具体说明编号符合 N. / N.M / N.M.K / N.M.K.L，缩进 4/8/12 空格，同级连续不跳号 | 抽查 + 脚本 |
| G5 | 证据充分 | 每个功能可追溯到功能盘点；无来源内容均标【待确认】并进附录 A | 回溯功能盘点 |
| G6 | 交互深度 | 按钮/列表/表单/状态均有三要素与交互反馈，无「只写静态布局」的条目 | 抽查每个功能 |
| G7 | 可测性 | 生成测试用例时，叶子条目与限制条件 100% 有覆盖用例 | 反向核对 |

| G9 | 语言与占位 | 无字面量 HTML 实体、无模板占位残留（`yyyy-mm-dd`、`xxx`、`【此处插入原型图` 等）、无口语与营销话术 | 脚本 + 通读 |

不通过时必须修复后重跑检查；修复循环上限 3 轮，仍有未通过项须在交付说明中列明，不得隐瞒。

## 8. 禁止事项

1. 编造代码中不存在的功能、数据、指标、时间、人名；不确定就标【待确认】。
2. 跳过功能盘点直接产出正文（用户明确要求「先按代码快速出草稿」时，也须在草稿中标注假设）。
3. 把技术实现细节当成需求描述（如「监听 useEffect」「走 Redux」），应转写为用户可感知的行为。
4. 只写静态布局、不写交互与状态；只写正常流程、不写异常与边界。
5. 自创章节、改变编号层级、用表格替代两列功能点结构。
6. 在 Word 中保留 markmap 代码块，或用 Word 原生表格 / 截图替代嵌入 Excel 测试用例。
7. 批量刷新「更新时间」、编造修订记录。
8. 一次输出超长导致在表格或字段中间截断；应主动分段。
9. 交付时只丢出文件路径、不说明遗留问题；或工具失败后静默降级。
